Workflow Engine 架构与行为分析

基于当前代码（internal/engine + internal/store + internal/workflow）

一、分层架构与依赖方向

包层级（自上而下）

cmd/server
main.go（入口 stub，尚未实现 HTTP/RPC）
internal/engine — 核心执行引擎
engine.go · executor.go · builtin.go · validate.go · execute.go · resolve.go · state.go · util.go
internal/workflow — 纯数据模型
model.go（Definition / Step / Run / StepExecution + 状态枚举）
internal/store — SQLite 持久化
store.go · definition.go · run.go · execution_state.go · helpers.go
依赖方向：cmd → engine → model；store 实现 engine 定义的 ExecutionStateStore 接口（依赖倒置，engine 不依赖 store 具体类型）。

engine 内部组件关系

组件职责
Engine持有 registry + stateStore，对外暴露 CreateRun / ExecuteStep / RunWorkflow
ExecutorRegistry按 stepType 注册/查找 StepExecutor（带 RWMutex）
StepExecutor 接口Execute(ctx, step, input) → (output, error)
ComputeExecutor从 step.Config 读 a+b，输出 result
DoubleExecutor从 input["value"] 乘 2，输出 result
validateDefinitionID/version/step 校验 + DFS 三色环检测
resolveStepInput按 Step.Inputs 的 InputRef 把上游 output 映射到 input map
ExecutionStateStore接口，SaveExecutionState 由 store 实现

二、一次执行的完整流程（ExecuteStep 九步）

1
终态检查
run 已 SUCCEEDED/FAILED 则拒绝执行
2
查 step 定义 + 执行记录 + 依赖状态
step 必须是 PENDING；所有 DependsOn 必须是 SUCCEEDED
3
查找 executor
按 step.Type 从 registry 取执行器
4
解析输入（resolveStepInput）
按 Inputs 映射，失败立即标记 step FAILED + run FAILED 并持久化
5
持久化 RUNNING（关键崩溃恢复点）
先写库确认 RUNNING；失败则回滚内存状态，绝不调用 executor
6
调用 executor.Execute
同步阻塞；内部检查 ctx.Done()
7
执行失败
step FAILED + run FAILED，持久化后返回 error
8
记录成功结果
step SUCCEEDED；若所有 step 都成功则 run SUCCEEDED
9
持久化最终状态
事务里同时 UPDATE step_executions 和 workflow_runs
绿色=持久化点 红色=失败路径

三、状态机

PENDING → RUNNING → SUCCEEDED 或 FAILED
  • RunStatus：PENDING → RUNNING → SUCCEEDED / FAILED
  • StepStatus：与 RunStatus 同构
  • run 状态由最后一个 step 成功自动翻转为 SUCCEEDED；任何 step 失败立即翻转为 FAILED
  • 终态不可逆：一旦 SUCCEEDED/FAILED，ExecuteStep 直接拒绝

四、调度模型（RunWorkflow）

↻
循环扫描 def.Steps
每轮按定义顺序找 PENDING 且依赖全成功的 step
▶
串行执行命中的 step
一次只跑一个；同层无依赖的 step 也不并行
✓
全部成功 → run SUCCEEDED 返回
✗
无进展（有 PENDING 但都不可跑）→ 报错返回
这是"死锁"检测：通常是因为某步失败后下游永远 PENDING

五、设计特点与局限

维度现状评价
持久化一致性 先写 RUNNING 再执行，失败回滚内存 优点崩溃恢复语义清晰：重启后只重跑 PENDING
依赖倒置 engine 定义 ExecutionStateStore 接口，store 实现它 优点engine 可单测，store 可替换
输入契约 统一通过 Step.Inputs 的 InputRef 显式映射 优点无隐式聚合，executor 只消费 input map
并发模型 串行 for 循环，同层 step 不并行 局限无 DAG 并行，吞吐受限
失败策略 单步失败即整个 run FAILED，无重试 局限无重试/补偿/忽略失败策略
调度方式 同步阻塞 RunWorkflow(ctx, ...) 局限无事件驱动/worker 池，长任务阻塞调用方
类型安全 input/output 都是 map[string]any 注意运行时类型断言，executor 内部需自己断言
Schema 迁移 CREATE TABLE IF NOT EXISTS 注意无版本化迁移表，改表结构需手动处理
时间/超时 executor 检查 ctx.Done()，但 RunWorkflow 本身不设超时 注意超时由调用方传 ctx 控制
可观测性 无日志、无 metric、无事件回调 局限只能靠查库看状态
